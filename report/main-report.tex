\addsec{Abstract}
This report investigates the real world power consumption of four home and \ac{SME} network devices, comparing measurements against manufacturer specifications.
The devices under test are the \texttt{Fritzbox~7530}, \texttt{Asus~RT-AX68U}, \texttt{Huawei~EG8245W5-8T}, and \texttt{Alcatel~HH40V}.

To measure this properly, I built a custom Go-based web application that generates customizable network load while logging power consumption from a \ac{DECT}~200 smart plug via the FritzBox TR-064 \ac{API}.
Five tests cover incremental Ethernet port loading, per-port throughput scaling, full subsystem profiling (Ethernet + Wi-Fi + \ac{USB} combined), Wi-Fi distance and band comparison, and bridge-mode efficiency.

Key findings: devices only reach 22--47\% of their provided power supply rated maximum power under full combined load, with my tests.
Wi-Fi radios are the dominant power consumer when active, drawing 7--8$\times$ more power per megabit than wired Ethernet.
Running an \ac{ISP} modem in bridge mode alongside a dedicated router increases combined idle power by about 86\% compared to using the modem standalone.
Built-in eco modes have varying effectiveness: the Fritzbox's eco mode saves 7--19\% but limits Ethernet throughput to $\sim$100\,Mbps/port, while Wi-Fi TX power reduction on the Asus and Huawei yields minimal savings.

\section{Introduction}
\label{sec:introduction}

Consumer to \ac{SME} network routers operate continuously, yet manufacturer specifications typically only state maximum power ratings (e.g., 18\,W or 33\,W). This report aims to quantify the baseline and load-dependent power consumption of these devices in typical configurations.

The following four devices were tested: a \verb|Fritzbox~7530| (\ac{ISP}-style router, 2018), an \verb|Asus~RT-AX68U| (Wi-Fi~6, 2020), a \verb|Huawei~EchoLife~EG8245W5-8T| (fiber \ac{ONT} from Energie AG), and an \verb|Alcatel~HH40V| (basic single-band, 2018). Stated power ratings range from 10--33\,W. To evaluate real-world power efficiency, power draw was empirically measured across these devices to determine how power consumption changes with Ethernet port count, Wi-Fi load, eco mode, or running in bridge mode.

To do this I built a custom Go application that generates controlled \ac{UDP} traffic on each Ethernet interface, polls the \ac{DECT}~200 smart plug via TR-064~\cite{bib:tr064}, and stores everything in a SQLite database. The source code is at \verb|github.com/MrCodeEU/jku-master-project-network-devices-power-consumption-analysis|. 

A few problems occured along the way: the smart plug only updates every two minutes by default (worked around via Home Assistant), one \ac{NIC} port was broken, and some routers had quirks resulting in deviations from the planned protocol -- all covered in the relevant sections.


\section{Research Questions}
\label{sec:research-questions}
These questions where originally phrased differentlly but naturally changed while testing and running the experiments. The final versions are:
\begin{enumerate}
    \item[\textbf{RQ1}] How does power consumption change with the number of active Ethernet ports?
    \label{rq:ports}
    \item[\textbf{RQ2}] What is the per-port power overhead of idle Ethernet connections, and how does it compare to the incremental cost of active network traffic?
    \label{rq:port-overhead}
    \item[\textbf{RQ3}] How does power consumption scale with network load (idle, 50\%, 100\% utilization of bandwidth)?
    \label{rq:load-scaling}
    \item[\textbf{RQ4}] Which equipment is suitable for continuous operation and which devices have high idle consumption that makes them candidates for automated shutdown during the night?
    \label{rq:idle-suitability}
    \item[\textbf{RQ5}] How does Wi-Fi affect router power consumption, and how do factors such as frequency band (2.4 vs.\ 5\,GHz), number of connected clients, and signal strength (distance to access point) influence it?
    \label{rq:wifi-impact}
    \item[\textbf{RQ6}] What is the actual impact of manufacturer-provided power-saving modes (e.g., Fritzbox \verb|Green Mode|, Wi-Fi transmission power control) on overall power consumption?
    \label{rq:power-saving}
    \item[\textbf{RQ7}] Does a device's maximum power consumption rating correlate with its real-world power usage under typical operating conditions, and what does it take to reach that level?
    \label{rq:rated-vs-real}
    \item[\textbf{RQ8}] How efficient is \ac{ISP}-provided equipment (e.g., Huawei router or Fritzbox 7530) when operating in bridge mode compared to dedicated networking equipment?
    \label{rq:bridge-mode}
\end{enumerate}

\section{Setup}
\label{sec:setup}
    \subsection{Hardware}
    The four devices under test are routers and modems I had available -- a mix of \ac{ISP}-provided equipment and personally-owned hardware:
    \begin{description}
        \item[Fritzbox 7530] (2018, 802.11ac, 4$\times$ \ac{GbE}, rated 18\,W max~\cite{bib:datasheet-fritzbox7530}) -- \ac{ISP}-style ADSL/VDSL router, also used as the dedicated power-data collection device
        \item[Asus RT-AX68U] (2020, 802.11ax, 4$\times$ \ac{GbE}, rated 33\,W max~\cite{bib:datasheet-asus-rtax68u}) -- high-end consumer Wi-Fi~6 router
        \item[Huawei EchoLife EG8245W5-8T] (2020, 802.11ax, 4$\times$ \ac{GbE}, rated 24\,W max~\cite{bib:datasheet-huawei-eg8245}) -- fiber/GPON \ac{ONT} modem provided by Energie AG
        \item[Alcatel HH40V] (2018, 802.11n, 2$\times$ 100\,Mbps, rated 10\,W max~\cite{bib:datasheet-alcatel-hh40v}) -- basic budget \ac{ISP} modem
    \end{description}
    \subsection{Sampling Rate and Accuracy of Power Meter}
    The \ac{DECT}~200 accuracy is rated at $\pm 100$\,mW below 5\,W and $\pm 2$\% above 5\,W~\cite{bib:dect200}, giving $\sim$70\,mW effective resolution as per my testing which is sufficient for this project.

    By default the plug only updates its reading every two minutes. Longer phases are therefore needed for meaningful averages -- which is why Test~1 is significantly longer than the others. The workaround (found after the first test): the \ac{DECT}~200 refreshes whenever it receives any command. A Home Assistant automation sends \verb|turn on| every 15 seconds, and the test app polls via TR-064 every 5 seconds, effectively getting a fresh reading every $\sim$15\,s \cite{ha-dect-workaround}.
    % code for home assistant script
    \begin{lstlisting}[language=yaml]
alias: Automation - Nudge FritzDECT Smart Plug
description: ""
triggers:
  - trigger: time_pattern
    seconds: /15
conditions:
  - condition: state
    entity_id: switch.fritz_dect_200
    state: "on"
  - condition: time
    after: "06:30:00"
    before: "23:59:00"
actions:
  - action: switch.turn_on
    target:
      entity_id: switch.fritz_dect_200
mode: single
    \end{lstlisting}

    \subsubsection{Getting Network Connectivity Right}
    \label{sec:network-setup}
    The test PC has a 4-port 2.5\,\ac{GbE} \ac{NIC}, but port~4 turned out to be broken (links up, drops all frames). The workaround was three \ac{NIC} ports plus the motherboard Intel I225-V port.

    Each \ac{DUT} uses a different default subnet, so the test PC interfaces needed manual IP configuration before each run. Example for the Fritzbox (192.168.188.x):

    \begin{lstlisting}[language=PowerShell]
# Remove old addresses and assign FritzBox subnet IPs
Remove-NetIPAddress -InterfaceAlias "Ethernet 5" -Confirm:$false -ErrorAction SilentlyContinue
New-NetIPAddress -InterfaceAlias "Ethernet 5" -IPAddress 192.168.188.3 -PrefixLength 16
New-NetIPAddress -InterfaceAlias "Ethernet 7" -IPAddress 192.168.188.4 -PrefixLength 16
New-NetIPAddress -InterfaceAlias "Ethernet"   -IPAddress 192.168.188.5 -PrefixLength 16
New-NetIPAddress -InterfaceAlias "Ethernet 6" -IPAddress 192.168.188.6 -PrefixLength 16
    \end{lstlisting}

    Subnets per device: FritzBox 192.168.188.x, Huawei 192.168.18.x, Asus 192.168.51.x, Alcatel 192.168.1.x.
    Static host routes were added so each interface reached the \ac{DUT}'s management IP without relying on Windows' routing:

    \begin{lstlisting}[language=PowerShell]
# Routes to Huawei gateway, different metric per interface
New-NetRoute -DestinationPrefix "192.168.18.1/32" -InterfaceAlias "Ethernet 5" `
    -NextHop "0.0.0.0" -RouteMetric 2
New-NetRoute -DestinationPrefix "192.168.18.1/32" -InterfaceAlias "Ethernet 7" `
    -NextHop "0.0.0.0" -RouteMetric 3
    \end{lstlisting}

    Connectivity was verified with \texttt{ping} and \texttt{Test-NetConnection} before each run via the test app's web UI.

    \subsection{Automating Testing and Data Collection}
    \label{sec:automation}
    To make measurements reproducible, I built a custom web application with a Go backend and JavaScript frontend. Source at \texttt{github.com/MrCodeEU/jku-master-project-network-devices-power-consumption-analysis}.

    \subsubsection{Architecture Overview}
    The application consists of a few cooperating components:
    \begin{description}
        \item[Test Runner (\texttt{runner.go})] Orchestrates three phases (pre-test baseline, load with per-interface ramping, post-test baseline). Durations, interface order, and ramp steps are all configurable from the web UI.
        \item[Load Generator (\texttt{loadgen.go})] Generates \ac{UDP} flooding, \ac{TCP}, or raw L2 frames. Per-interface rate limiting uses nanosecond-precision spin-wait. \ac{UDP} flooding was the mode used for all Ethernet tests.
        \item[Power Meter Interface (\texttt{fritzbox.go})] Reads power from the \ac{DECT}~200 via TR-064 \ac{SOAP}~\cite{bib:tr064} using \texttt{gofritz}~\cite{bib:gofritz}. Always talks to the dedicated collection FritzBox, never the \ac{DUT}.
        \item[Web Server (\texttt{server.go})] REST \ac{API} + \ac{SSE} for real-time browser streaming. Results persisted in SQLite.
        \item[Analysis Dashboard (\texttt{analysis.js})] Computes per-phase stats (avg, std dev, min/max, Mbps/W) and renders Chart.js visualizations. Exports \ac{CSV}, Excel, and pgfplots \LaTeX~\cite{bib:pgfplots} -- the latter is how some of the figures in this report were generated.
    \end{description}

    \subsubsection{Load Generation Approach}
    Three methods were tried: \textbf{\ac{TCP}} topped out at 60--80\,Mbps (routers rate-limit unsolicited connections to their own IP in some way i suppose). \textbf{Raw L2 frames} via \texttt{libpcap} were capped at $\sim$550\,Mbps on Windows due to OS scheduling, this could have been improved with different libraries or approaches maybe but \ac{UDP} flooding was sufficient. \textbf{\ac{UDP} flooding} near line-rate (3.85\,Gbps aggregate on the Huawei at 4$\times$1\,\ac{GbE}) using 1400-byte packets, 16 workers/interface, 10-packet batches.

    All traffic targets the \ac{DUT}'s own IP address, forcing \ac{CPU} processing -- similar to heavy NAT load, not pure L2 switching. While this is not a perfect emulation, as the cpu load will be significantlly higher then for real-world traffic, it provides a consistent and repeatable load that stresses the device's processing capabilities, and forcing higher power consuption.

    In addition to the custom \ac{UDP}/\ac{TCP}/Layer~2 load generator, \textbf{iperf3}~\cite{bib:iperf3} was used for Wi-Fi throughput testing.
    The load generation tool integrates iperf3 as a subprocess, parsing its per-second output to record throughput alongside power data.
    For phone-to-phone Wi-Fi load tests (Test~3), an Android iperf3 app~\cite{bib:iperf3-android} was used to generate traffic between two smartphones connected to the \ac{DUT}'s Wi-Fi network.
    For Wi-Fi-to-\ac{LAN} tests (Test~4), the iperf3 server ran on the test PC while a Wi-Fi client device acted as the iperf3 client, routing traffic through the \ac{DUT}.

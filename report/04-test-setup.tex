\section{Test Setups}

This section describes the five test setups, covering \ac{DUT}, topology, traffic generation, and protocol. Practical deviations are noted where relevant.

\subsection{Test~1: Incremental Port Load Test (Completed)}
\label{sec:test-incremental-port-load}
% ---------------------------------------------------------------------------

Incrementally loads 1--4 Ethernet ports with maximum \ac{UDP} traffic, directly addressing \textbf{RQ1} and partially \textbf{RQ4} and \textbf{RQ7}.

\subsubsection{Devices Under Test}
All four devices (as described in Section~\ref{sec:setup}): \verb|Fritzbox~7530|, \verb|Asus~RT-AX68U|, \verb|Huawei~EG8245W5-8T|, \verb|Alcatel~HH40V|.

\subsubsection{Physical Topology}
The PC connects 1--4 Ethernet cables to the \ac{DUT}, which is powered through the \ac{DECT}~200 smart plug. A separate \verb|Fritzbox~7490| (not under test) hosts the \ac{DECT}~200 base station and TR-064 \ac{API} -- see Figure~\ref{fig:test1_topology}.

\subsubsection{Test Protocol}
Each device was tested using the following automated protocol, executed by the custom web application described in Section~\ref{sec:automation}:
\begin{enumerate}
    \item \textbf{Pre-test baseline} (10\,min): All Ethernet cables connected but no traffic generated. Measures idle power with active link-up on all ports.
    \item \textbf{Load phase~1} (20\,min): Maximum \ac{UDP} flood on \textbf{1~port} (target: 1\,Gbps).
    \item \textbf{Load phase~2} (20\,min): Maximum \ac{UDP} flood on \textbf{2~ports} (target: 2\,Gbps).
    \item \textbf{Load phase~3} (20\,min): Maximum \ac{UDP} flood on \textbf{3~ports} (target: 3\,Gbps). \emph{Skipped for \texttt{Alcatel~HH40V} (only 2 ports).}
    \item \textbf{Load phase~4} (20\,min): Maximum \ac{UDP} flood on \textbf{4~ports} (target: 4\,Gbps). \emph{Skipped for Alcatel.}
    \item \textbf{Post-test baseline} (20\,min): All traffic stopped, cables remain connected. Measures power recovery behavior.
\end{enumerate}

\noindent\textbf{Load generation parameters:}
\begin{itemize}
    \item Protocol: \ac{UDP}, packet size: 1400\,bytes, 16 workers per interface
    \item Target: device's own IP address (e.g., \texttt{169.254.1.1:80} for Fritzbox)
    \item Interfaces activated incrementally with 5 ramp-up steps per interface
    \item Power polling interval: 5\,seconds (via TR-064 SOAP \ac{API})
\end{itemize}

\noindent\textbf{Important limitation:} Traffic is directed at the \ac{DUT}'s own IP address, meaning all packets are processed by the device's \emph{\ac{CPU}/software stack}. This represents a \ac{CPU}-intensive workload (similar to, but likely much higher than, heavy NAT processing or connection handling) rather than pure L2 forwarding. As a result, devices with weaker CPUs (notably the \verb|Fritzbox~7530|) show throughput degradation at higher port counts due to \ac{CPU} saturation, not switching fabric limitations.

\subsection{Test~2: Throughput Scaling (Single Port)}
\label{sec:test-throughput-scaling}

Single-port throughput ramp from 0 to line rate, directly addressing \textbf{RQ2} and \textbf{RQ3}. Comparing single-cable idle with Test~1's four-cable idle quantifies per-port overhead.

\subsubsection{Test Protocol}
The test uses the load generator's built-in \emph{ramp steps} feature, which increases the per-interface rate limit in equal increments:
\begin{enumerate}
    \item \textbf{Pre-test baseline} (5\,min): 1 cable connected, no traffic.
    \item \textbf{Load phase} (25\,min total): Single port, \ac{UDP}, \texttt{ramp\_steps=4}, \texttt{target\_mbps=1000}.
    The load generator automatically steps through:
    \begin{itemize}
        \item Step~1: $\sim$250\,Mbps (25\% of link capacity)
        \item Step~2: $\sim$500\,Mbps (50\%)
        \item Step~3: $\sim$750\,Mbps (75\%)
        \item Step~4: $\sim$1000\,Mbps (100\%)
    \end{itemize}
    \item \textbf{Post-test baseline} (5\,min): Traffic stopped, cable remains connected.
\end{enumerate}

\noindent\textbf{Load generation parameters:}
\begin{itemize}
    \item Protocol: \ac{UDP}, packet size: 1400\,bytes, 10 workers
    \item Single interface enabled, \texttt{ramp\_duration} = 0 (auto, equals load duration)
    \item Target: \ac{DUT}'s own IP address (consistent with Test~1)
    \item Power polling interval: 5\,seconds
\end{itemize}

\subsection{Test~3: Incremental Subsystem Power Profiling}
\label{sec:test-subsystem-profiling}
% ---------------------------------------------------------------------------

Progressively enables every subsystem from bare power-on to full combined load. Six groups are recorded as separate runs and combined for analysis. Two runs per device: Run~A (defaults) and Run~B (manufacturer power-saving modes). Addresses \textbf{RQ2}, \textbf{RQ4}, \textbf{RQ5}, \textbf{RQ6}, and \textbf{RQ7}.

\subsubsection{Devices Under Test}
All four devices. The Alcatel (2$\times$100\,Mbps, 2.4\,GHz only, no \ac{USB}) skips groups it is not capable of.

\subsubsection{Physical Topology}
Same as Test~1. Two smartphones act as Wi-Fi clients (one per band), for Groups~5--6, an Android iperf3 app generates phone-to-phone Wi-Fi traffic through the \ac{DUT}.

\subsubsection{Group Design}
Six groups cumulatively add subsystems (Figure~\ref{fig:test3_phase_diagram}). Individual cable additions are retained because Test~1 starts with all cables connected and cannot isolate the per-cable \ac{PHY} cost.

\subsubsection{Test Protocol --- Run~A (Default Settings)}
Subsystems are added \emph{cumulatively}. Each group is a separate run (1\,min pre-baseline, 1--2\,min measurement at 5\,s polling); manual intervention between groups modifies the physical setup. This is also the reason why the tests are split into multiple groups instead of a single run with all transitions, to keep the measurement phases clean and comparable across devices.

\begin{description}
    \item[Group~1] Device on, all Wi-Fi off, no cables. Record bare minimum, then add cables \emph{one at a time} ($\sim$2\,min each) with custom events marking each insertion.
    \item[Group~2] Attach \ac{USB} storage devices one at a time. \emph{Skipped for Alcatel (no \ac{USB}).}
    \item[Group~3] Enable Wi-Fi radios: 2.4\,GHz first, then 5\,GHz after $\sim$2\,min (no clients). \emph{Alcatel: 2.4\,GHz only. Fritzbox: both bands enable together.}
    \item[Group~4] Connect smartphones: one to 2.4\,GHz, one to 5\,GHz (idle, no traffic).
    \item[Group~5] iperf3 flood between the two phones via Android app; tool records power only.
    \item[Group~6] Wi-Fi iperf3 flood continues + simultaneous max \ac{UDP} on all Ethernet ports.
\end{description}

\subsubsection{Test Protocol --- Run~B (Power-Saving Modes)}
Run~B repeats Groups~3--6 with manufacturer-provided power-saving modes enabled.
Since power-saving features primarily affect Wi-Fi transmission power and (for some devices) Ethernet \ac{PHY} settings, Groups~1--2 (bare minimum, cables, \ac{USB}) are not repeated; the Run~A data is reused for those groups.
The following power-saving settings were applied:
\begin{itemize}
    \item \textbf{Fritzbox 7530:} Full eco mode enabled (System $\rightarrow$ Energy Monitor $\rightarrow$ \texttt{Green Mode}), which reduces Ethernet \ac{PHY} power, Wi-Fi transmission power, and dims LEDs.
    The Fritzbox eco mode was the only one to affect Ethernet, so a \emph{full} rerun of all groups (1--6) was performed.
    \item \textbf{Asus RT-AX68U:} Wi-Fi TX power set to the lowest available setting for both bands.
    \item \textbf{Huawei EG8245W5-8T:} Wi-Fi TX power set to 20\% for both bands.
    \item \textbf{Alcatel HH40V:} No power-saving features available; Run~B was skipped.
\end{itemize}

\subsubsection{Measurement Considerations}
Because each group is recorded as a separate test run, minor power discontinuities may appear when combining the data across groups.
In practice, the observed jumps were small (typically $<$100\,mW) and certainly do not affect the analysis.

\subsubsection{Research Questions Addressed}
\begin{description}
    \item[RQ2:] Group~1 isolates the per-port \ac{PHY} link-up cost by adding cables individually, complementing the per-port load data from Test~1.
    \item[RQ4:] The bare-minimum measurement in Group~1 provides the absolute power floor.
    \item[RQ5:] Groups~3--5 isolate the idle cost of Wi-Fi radios, client associations, and active Wi-Fi load. Individual-band throughput measurements are covered in detail by Test~4.
    \item[RQ6:] Direct comparison of Run~A vs.\ Run~B at each group quantifies savings from manufacturer eco/power-saving modes.
    \item[RQ7:] Group~6 loads all subsystems simultaneously, providing the closest approximation to the rated maximum power.
\end{description}

\subsubsection{Practical Notes and Challenges}
Device-specific notes:
\begin{itemize}
    \item \textbf{Fritzbox bands}: Both 2.4/5\,GHz radios switch on/off together -- impossible to isolate per-band cost in Group~3.
    \item \textbf{Fritzbox port anomaly}: One port (``Ethernet~7'') reported $\sim$25\,000\,Mbps during Group~6 -- the \ac{NIC} was counting retransmitted frames. The other three ports showed normal $\sim$461\,Mbps each; Group~6 throughput was estimated by multiplying that average by four. Power data was unaffected.
    \item \textbf{Power-saving modes}: Alcatel has none -- Run~B skipped. Fritzbox eco mode also throttles Ethernet \ac{PHY} to $\sim$100\,Mbps, so a full six-group rerun was done for it rather than just Groups~3--6.
\end{itemize}

\subsection{Test~4: Wi-Fi Signal Strength and Distance}
\label{sec:test-wifi-distance}
% ---------------------------------------------------------------------------

This test measures the effect of frequency band (2.4\,GHz vs.\ 5\,GHz), physical distance, and effect of walls on Wi-Fi power consumption and throughput. It addresses \textbf{RQ5}.

\subsubsection{Devices Under Test}
All four devices are tested:
\begin{itemize}
    \item \textbf{Asus RT-AX68U} (802.11ax, dual-band 2.4 + 5\,GHz, 160\,MHz capable)
    \item \textbf{Fritzbox 7530} (802.11ac, dual-band 2.4 + 5\,GHz)
    \item \textbf{Huawei EG8245W5-8T} (802.11ax, dual-band 2.4 + 5\,GHz)
    \item \textbf{Alcatel HH40V} (802.11n, 2.4\,GHz only)
\end{itemize}

\subsubsection{Physical Setup}
\begin{itemize}
    \item \textbf{Near position:} Client device $<$2\,m from \ac{DUT}, line of sight.
    \item \textbf{Wall position:} Client device $\sim$10\,m from \ac{DUT}, through one interior wall.
\end{itemize}
The \ac{DECT}~200 measures \ac{DUT} power.
For the Asus, Fritzbox, and Alcatel, a Wi-Fi client device runs iperf3 to the test PC connected via Ethernet \ac{LAN}.
The load generator tool records both power and throughput inline.

\subsubsection{Test Protocol}
Each scenario (device $\times$ band $\times$ distance) is a separate 5-minute run: 1\,min idle baseline, 3\,min iperf3 \ac{TCP} flood, 1\,min post-test baseline.
Dual-band devices are tested four times (2 bands $\times$ 2 distances); the Alcatel is tested twice (2 distances on 2.4\,GHz only).

\subsubsection{Device-Specific Deviations}

\begin{itemize}
    \item{Fritzbox: Both radios always active.}
The \verb|Fritzbox~7530| firmware does not allow disabling individual radio bands.
Both the 2.4\,GHz and 5\,GHz radios remain active during all tests.
The idle baseline therefore includes the power draw of both radios, and tests labelled ``5\,GHz'' or ``2.4\,GHz'' reflect which band carries the iperf3 traffic while the other radio is idle.
    \item{Huawei: Wi-Fi client isolation.}
The Huawei~EG8245W5-8T isolates \ac{LAN} and Wi-Fi clients by default (and i was not able to find a way to turn it off), preventing iperf3 from running between a wired PC and a Wi-Fi client. Throughput is captured separately from the iperf3 terminal output (1-second intervals, averaged to 5-second bins for analysis).
    \item{Alcatel: 100\,Mbps \ac{LAN} bottleneck.}
The Alcatel has only two 100\,Mbps Ethernet ports, creating a potential throughput bottleneck.
To verify, additional ``both Wi-Fi'' tests were performed with the test PC also connected via Wi-Fi, bypassing the \ac{LAN} entirely.
\end{itemize}

\subsection{Test~5: \ac{ISP} Bridge Mode Comparison}

It directly addresses \textbf{RQ8}.

\begin{description}
    \item[Configuration~A (Standalone):] Huawei EG8245W5-8T operating as router (NAT, DHCP, Wi-Fi, firewall).

    \item[Configuration~B (Split):] Huawei EG8245W5-8T in bridge mode (minimal processing) + Asus RT-AX68U as dedicated router.

\subsubsection{Test Protocol}
Both configurations are tested with the same incremental port load profile as Test~1 for direct comparability:
\begin{enumerate}
    \item \textbf{Pre-test baseline} (10\,min): Cables connected, no traffic.
    \item \textbf{Load phases} (4$\times$20\,min): Incremental 1--4 port \ac{UDP} flood.
    \item \textbf{Post-test baseline} (10\,min): Traffic stopped.
\end{enumerate}

\paragraph{Configuration~A:}
Reuses the Huawei standalone measurements from Test~1 (Section~\ref{sec:results-huawei}).
Because the load profile, traffic parameters, and power metering setup are identical, no additional measurement run is needed; the Huawei Test~1 data serves directly as the single-device baseline.

\paragraph{Configuration~B:}
\begin{itemize}
    \item Huawei set to bridge mode via its admin interface (disables NAT, DHCP, firewall, optionally Wi-Fi).
    \item Asus RT-AX68U configured as the primary router (WAN port connected to Huawei's \ac{LAN} port).
    \item Test PC connects to the Asus's \ac{LAN} ports.
    \item \textbf{Power measurement:} Both devices on a single \ac{DECT}~200 via a power strip to get the combined power consumption.
\end{itemize}

\noindent\textbf{Load generation parameters:} Identical to Test~1 (\ac{UDP}, 1400\,bytes, 16 workers, 5\,s polling).

\subsubsection{Practical Notes}
Reaching the Huawei's management IP (192.168.18.1) from the test PC (in the Asus's 192.168.51.x subnet) required two routing changes:
\begin{enumerate}
    \item On the \textbf{Asus router}: add a static route sending 192.168.18.0/24 traffic out via the WAN interface.
    \item On the \textbf{test PC}: add a persistent route pointing to the Huawei's specific IP via the Asus's \ac{LAN} IP:
\end{enumerate}

\begin{lstlisting}[language=PowerShell]
# On Windows test PC: route to Huawei's management IP via the Asus router
route -p add 192.168.18.1 mask 255.255.255.255 192.168.51.1 metric 1
\end{lstlisting}

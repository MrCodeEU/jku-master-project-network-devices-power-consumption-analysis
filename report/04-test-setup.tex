\subsection{Test~1: Incremental Port Load Test (Completed)}
\label{sec:test-incremental-port-load}
% ---------------------------------------------------------------------------

This test investigates how power consumption changes as Ethernet ports are incrementally loaded with maximum UDP traffic.
It directly addresses \textbf{RQ1} (power vs.\ number of active ports) and provides partial data for \textbf{RQ4} (idle power suitability for continuous operation) and \textbf{RQ7} (rated vs.\ real-world maximum power).

\subsubsection{Devices Under Test}
Four devices were tested, representing a range of consumer and ISP-provided equipment:
\begin{description}
    \item[Fritzbox 7530] (2018, 802.11ac, 4$\times$ GbE LAN, rated 18\,W max)
    \item[Asus RT-AX68U] (2020, 802.11ax, 4$\times$ GbE LAN, rated 33\,W max)
    \item[Huawei EchoLife EG8245W5-8T] (2020, 802.11ax, 4$\times$ GbE LAN, rated 24\,W max)
    \item[Alcatel HH40V] (2018, 802.11n, 2$\times$ 100\,Mbps LAN, rated 10\,W max)
\end{description}

\subsubsection{Physical Topology}
Figure~\ref{fig:test1_topology} shows the physical test setup.
The PC (equipped with a 4-port 2.5\,GbE NIC) connects 1--4 Ethernet cables to the device under test (DUT), which is powered through the DECT~200 smart plug for power measurement.
A \emph{separate} Fritzbox~7530 (not under test) hosts the DECT~200 base station and provides the TR-064 API endpoint for reading power data.
This isolation is critical: under heavy CPU load, the DUT's management API becomes unresponsive, which would cause measurement gaps if the DUT itself were used for data collection.

\subsubsection{Test Protocol}
Each device was tested using the following automated protocol, executed by the custom web application described in Section~\ref{sec:automation}:
\begin{enumerate}
    \item \textbf{Pre-test baseline} (10\,min): All Ethernet cables connected but no traffic generated. Measures idle power with active link-up on all ports.
    \item \textbf{Load phase~1} (20\,min): Maximum UDP flood on \textbf{1~port} (target: 1\,Gbps).
    \item \textbf{Load phase~2} (20\,min): Maximum UDP flood on \textbf{2~ports} (target: 2\,Gbps).
    \item \textbf{Load phase~3} (20\,min): Maximum UDP flood on \textbf{3~ports} (target: 3\,Gbps). \emph{Skipped for Alcatel~HH40V (only 2 ports).}
    \item \textbf{Load phase~4} (20\,min): Maximum UDP flood on \textbf{4~ports} (target: 4\,Gbps). \emph{Skipped for Alcatel.}
    \item \textbf{Post-test baseline} (20\,min): All traffic stopped, cables remain connected. Measures power recovery behavior.
\end{enumerate}

\noindent\textbf{Load generation parameters:}
\begin{itemize}
    \item Protocol: UDP, packet size: 1400\,bytes, 16 workers per interface
    \item Target: device's own IP address (e.g., \texttt{169.254.1.1:80} for Fritzbox)
    \item Interfaces activated incrementally with 5 ramp-up steps per interface
    \item Power polling interval: 5\,seconds (via TR-064 SOAP API)
\end{itemize}

\noindent\textbf{Important limitation:} Traffic is directed at the DUT's own IP address, meaning all packets are processed by the device's \emph{CPU/software stack}, not merely switched at Layer~2 by the switching ASIC. This represents a CPU-intensive workload (similar to heavy NAT processing or connection handling) rather than pure L2 forwarding. As a result, devices with weaker CPUs (notably the Fritzbox~7530) show throughput degradation at higher port counts due to CPU saturation, not switching fabric limitations.

\subsubsection{Research Questions Addressed}
\begin{description}
    \item[RQ1 (Fully addressed):] The test directly measures power at 0, 1, 2, 3, and 4 active loaded ports, providing a complete port-count vs.\ power profile for each device.
    \item[RQ4 (Partially addressed):] The 10-minute pre-test baseline provides idle power measurements (with cables connected) for all four devices, enabling an idle power comparison and annual energy cost estimation. A full 24-hour idle measurement is not captured.
    \item[RQ7 (Partially addressed):] By comparing the maximum observed power under full Ethernet load to the manufacturer's rated maximum, we can assess how close real-world usage comes to the rated specification. This test does not activate Wi-Fi or USB peripherals, so the absolute maximum is not reached.
\end{description}

\subsection{Test~2: Throughput Scaling (Single Port)}
\label{sec:test-throughput-scaling}
% ---------------------------------------------------------------------------

This test measures how power consumption scales with network throughput on a single Ethernet port.
It directly addresses \textbf{RQ2} (per-port idle overhead) and \textbf{RQ3} (power vs.\ throughput at intermediate load levels).
By comparing the single-cable idle power of this test with the four-cable idle power of Test~1, the per-port power overhead is quantified.

\subsubsection{Devices Under Test}
All four devices from Test~1.
The three GbE devices (Fritzbox~7530, Huawei~EG8245W5, Asus~RT-AX68U) are tested with a 1\,Gbps link and target throughput up to 1000\,Mbps.
The Alcatel~HH40V (100\,Mbps ports) is tested with its native link speed and a target of 100\,Mbps.

\subsubsection{Physical Topology}
The physical topology is identical to Test~1 (Figure~\ref{fig:test1_topology}), but with only a \emph{single} Ethernet cable from the test PC to the DUT.
Power is measured via the DECT~200 smart plug.
Figure~\ref{fig:test2_ramp_profile} shows the throughput profile for the ramp-step load generation.

\subsubsection{Test Protocol}
The test uses the load generator's built-in \emph{ramp steps} feature, which linearly increases the per-interface rate limit in equal increments:
\begin{enumerate}
    \item \textbf{Pre-test baseline} (5\,min): 1 cable connected, no traffic.
    \item \textbf{Load phase} (25\,min total): Single port, UDP, \texttt{ramp\_steps=4}, \texttt{target\_mbps=1000}.
    The load generator automatically steps through:
    \begin{itemize}
        \item Step~1: $\sim$250\,Mbps (25\% of link capacity)
        \item Step~2: $\sim$500\,Mbps (50\%)
        \item Step~3: $\sim$750\,Mbps (75\%)
        \item Step~4: $\sim$1000\,Mbps (100\%)
    \end{itemize}
    \item \textbf{Post-test baseline} (5\,min): Traffic stopped, cable remains connected.
\end{enumerate}

\noindent\textbf{Load generation parameters:}
\begin{itemize}
    \item Protocol: UDP, packet size: 1400\,bytes, 10 workers
    \item Single interface enabled, \texttt{ramp\_duration} = 0 (auto, equals load duration)
    \item Target: DUT's own IP address (consistent with Test~1)
    \item Power polling interval: 5\,seconds
\end{itemize}

\subsubsection{Research Questions Addressed}
\begin{description}
    \item[RQ2 (Fully addressed):] Comparing the single-cable idle power from this test with the four-cable idle power from Test~1 isolates the per-port idle overhead. Additionally, comparing idle power with load-step power reveals whether idle ports or active traffic dominate the power budget.
    \item[RQ3 (Fully addressed):] The four-step ramp produces a power-vs-throughput curve at 25\%, 50\%, 75\%, and 100\% utilization, revealing whether power scales linearly, sub-linearly, or in discrete steps.
\end{description}

\subsection{Test~3: Incremental Subsystem Power Profiling}
\label{sec:test-subsystem-profiling}
% ---------------------------------------------------------------------------

This test progressively enables every subsystem of the router---from bare power-on to maximum combined load---to reveal the marginal power cost of each component.
Rather than a single continuous measurement, the test is divided into six groups of related subsystems, with manual intervention between groups to connect cables, attach peripherals, enable radios, and start load tests.
Each group is recorded as a separate measurement run using the test application, which are later combined for analysis.
Two complete runs are performed per device: Run~A with default settings and Run~B with manufacturer-provided power-saving modes enabled.

It directly addresses \textbf{RQ2} (per-port PHY cost), \textbf{RQ4} (idle suitability), \textbf{RQ5} (Wi-Fi radio idle cost), \textbf{RQ6} (power-saving modes), and \textbf{RQ7} (reaching rated maximum).

\subsubsection{Devices Under Test}
All four devices from Test~1.
The Alcatel~HH40V has limited capabilities (2$\times$100\,Mbps, 2.4\,GHz only, no USB, no 5\,GHz radio) and skips inapplicable groups.

\subsubsection{Physical Topology}
The test PC connects via Ethernet (cables are added incrementally during Group~1) and, for devices that allow LAN--Wi-Fi communication, serves as the iperf3 target for Wi-Fi throughput testing.
Two smartphones act as Wi-Fi clients: one on 2.4\,GHz and one on 5\,GHz.
For Wi-Fi load in Groups~5 and~6, an Android iperf3 app generates traffic between the two phones through the DUT.
Power is measured via the DECT~200 smart plug (separate data-collection Fritzbox as in Test~1).

\subsubsection{Group Design}

The test is organised into six groups that cumulatively add subsystems.
Since Test~4 covers individual Wi-Fi band throughput measurements in detail, this test does not include separate per-band Wi-Fi load phases.
Individual Ethernet cable additions are retained because Test~1 measures per-port overhead with \emph{all} cables already connected, which does not isolate the PHY link-up cost of each additional cable.

Figure~\ref{fig:test3_phase_diagram} illustrates the group sequence.

\subsubsection{Test Protocol --- Run~A (Default Settings)}
Subsystems are added \emph{cumulatively}---nothing is removed between groups.
Each group is recorded as a separate run by the test application (1\,min pre-test baseline, 1--2\,min measurement at 5\,s polling).
Manual intervention occurs between groups to modify the physical setup.

\begin{description}
    \item[Group~1 --- Bare Minimum + Ethernet Cables:] The device is powered on with all Wi-Fi radios disabled and no cables connected.
    After recording the bare-minimum power floor ($\sim$3\,min), Ethernet cables are connected \emph{one at a time} with $\sim$2\,min between each addition.
    Custom events in the test application mark each cable insertion.
    This isolates the PHY link-up cost of each individual port.

    \item[Group~2 --- +USB Devices:] With all Ethernet cables still connected, USB storage devices are attached to the DUT's USB port(s) one at a time ($\sim$2\,min each).
    Measures USB peripheral power overhead.
    \emph{Skipped for Alcatel (no USB ports).}

    \item[Group~3 --- +Wi-Fi Radios ON:] With cables and USB still attached, Wi-Fi radios are enabled via the DUT's webUI.
    For dual-band devices, the 2.4\,GHz radio is enabled first, followed by the 5\,GHz radio after $\sim$2\,min.
    No clients are connected; this measures the idle radio power cost.
    \emph{Alcatel: 2.4\,GHz only. Fritzbox: both radios enable simultaneously (firmware limitation).}

    \item[Group~4 --- +Wi-Fi Clients Connected (Idle):] A smartphone connects to the 2.4\,GHz network and a second smartphone connects to the 5\,GHz network (both idle, no traffic).
    Measures the power overhead of client association and idle session maintenance.
    \emph{Alcatel: two 2.4\,GHz clients (no 5\,GHz).}

    \item[Group~5 --- Wi-Fi Load:] An iperf3 flood is started between the two Wi-Fi-connected smartphones using an Android iperf3 app.
    The test application records power with load generation disabled (Wi-Fi load is external).
    Wi-Fi throughput is noted manually from the iperf3 app output.
    This measures the power cost of active Wi-Fi data transfer without Ethernet load.

    \item[Group~6 --- All Subsystems Maximum Load:] The Wi-Fi iperf3 flood continues, and the test application simultaneously starts maximum UDP flooding on all Ethernet ports.
    This phase represents the closest approximation to the device's rated maximum power, with all subsystems active and under load.
\end{description}

\subsubsection{Test Protocol --- Run~B (Power-Saving Modes)}
Run~B repeats Groups~3--6 with manufacturer-provided power-saving modes enabled.
Since power-saving features primarily affect Wi-Fi transmission power and (for some devices) Ethernet PHY settings, Groups~1--2 (bare minimum, cables, USB) are not repeated; the Run~A data is reused for those groups.
The following power-saving settings were applied:
\begin{itemize}
    \item \textbf{Fritzbox 7530:} Full eco mode enabled (System $\rightarrow$ Energy Monitor $\rightarrow$ ``Green Mode''), which reduces Ethernet PHY power, Wi-Fi transmission power, and dims LEDs.
    The Fritzbox eco mode was the only one to affect Ethernet, so a \emph{full} rerun of all groups (1--6) was performed.
    \item \textbf{Asus RT-AX68U:} Wi-Fi TX power set to the lowest available setting for both bands.
    \item \textbf{Huawei EG8245W5-8T:} Wi-Fi TX power set to 20\% for both bands.
    \item \textbf{Alcatel HH40V:} No power-saving features available; Run~B was skipped.
\end{itemize}

\subsubsection{Alcatel Adaptation}
The Alcatel (2$\times$100\,Mbps, 2.4\,GHz only, no USB) uses a reduced group sequence:
Group~1 (bare minimum + 2 cables), Group~3 (2.4\,GHz radio), Group~4 (2.4\,GHz clients), Group~5 (Wi-Fi load), Group~6 (Wi-Fi + Ethernet max load).
Groups~2 (USB) is skipped entirely.

\subsubsection{Measurement Considerations}
Because each group is recorded as a separate test run, minor power discontinuities may appear when combining the data across groups.
These arise from slight environmental variations between consecutive runs (e.g., ambient temperature drift, power supply fluctuations).
In practice, the observed jumps were small (typically $<$100\,mW) and did not affect the analysis.

\subsubsection{Research Questions Addressed}
\begin{description}
    \item[RQ2:] Group~1 isolates the per-port PHY link-up cost by adding cables individually, complementing the per-port load data from Test~1.
    \item[RQ4:] The bare-minimum measurement in Group~1 provides the absolute power floor; subsequent groups characterise various idle configurations for annual energy cost projections.
    \item[RQ5:] Groups~3--5 isolate the idle cost of Wi-Fi radios, client associations, and active Wi-Fi load. Individual-band throughput measurements are covered in detail by Test~4.
    \item[RQ6:] Direct comparison of Run~A vs.\ Run~B at each group quantifies savings from manufacturer eco/power-saving modes.
    \item[RQ7:] Group~6 loads all subsystems simultaneously, providing the closest approximation to the rated maximum power.
\end{description}

\subsection{Test~4: Wi-Fi Signal Strength and Distance}
\label{sec:test-wifi-distance}
% ---------------------------------------------------------------------------

This test measures the effect of frequency band (2.4\,GHz vs.\ 5\,GHz), physical distance, and wall attenuation on Wi-Fi power consumption and throughput.
It addresses \textbf{RQ5}.

\subsubsection{Devices Under Test}
All four devices are tested:
\begin{itemize}
    \item \textbf{Asus RT-AX68U} (802.11ax, dual-band 2.4 + 5\,GHz, 160\,MHz capable)
    \item \textbf{Fritzbox 7530} (802.11ac, dual-band 2.4 + 5\,GHz)
    \item \textbf{Huawei EG8245W5-8T} (802.11ax, dual-band 2.4 + 5\,GHz)
    \item \textbf{Alcatel HH40V} (802.11n, 2.4\,GHz only)
\end{itemize}

\subsubsection{Physical Setup}
\begin{itemize}
    \item \textbf{Near position:} Client device $<$2\,m from DUT, line of sight.
    \item \textbf{Wall position:} Client device $\sim$10\,m from DUT, through one interior wall.
\end{itemize}
The DECT~200 measures DUT power.
For the Asus, Fritzbox, and Alcatel, a Wi-Fi client device runs iperf3 to the test PC connected via Ethernet LAN.
The load generator tool records both power and throughput inline.

\subsubsection{Test Protocol}
Each scenario (device $\times$ band $\times$ distance) is a separate 5-minute run: 1\,min idle baseline, 3\,min iperf3 TCP flood, 1\,min post-test baseline.
Dual-band devices are tested four times (2 bands $\times$ 2 distances); the Alcatel is tested twice (2 distances on 2.4\,GHz only).

\subsubsection{Device-Specific Deviations}

\paragraph{Fritzbox: Both radios always active.}
The Fritzbox~7530 firmware does not allow disabling individual radio bands.
Both the 2.4\,GHz and 5\,GHz radios remain active during all tests.
The idle baseline therefore includes the power draw of both radios, and tests labelled ``5\,GHz'' or ``2.4\,GHz'' reflect which band carries the iperf3 traffic while the other radio is idle.

\paragraph{Huawei: Wi-Fi client isolation.}
The Huawei~EG8245W5-8T isolates LAN and Wi-Fi clients by default, preventing iperf3 from running between a wired PC and a Wi-Fi client.
Instead, iperf3 runs between two Wi-Fi client devices communicating through the router.
Since the load generator cannot measure Wi-Fi throughput directly in this configuration, power is recorded by the tool (with load generation disabled), and iperf3 is started manually on the client.
Throughput is captured separately from the iperf3 terminal output (1-second intervals, averaged to 5-second bins for analysis).

\paragraph{Alcatel: 100\,Mbps LAN bottleneck.}
The Alcatel has only two 100\,Mbps Ethernet ports, creating a potential throughput bottleneck.
To verify, additional ``both Wi-Fi'' tests were performed with the test PC also connected via Wi-Fi, bypassing the LAN entirely.

\begin{description}
    \item[RQ5:] Comparing near vs.\ wall power for the same band isolates the effect of signal attenuation on DUT power consumption. Comparing 2.4\,GHz vs.\ 5\,GHz at the same distance reveals band-dependent power and throughput characteristics. Cross-device comparison quantifies how router hardware and Wi-Fi standard (802.11n/ac/ax) affect energy efficiency.
\end{description}

\subsection{Test~5: ISP Bridge Mode Comparison}
\label{sec:test-bridge-mode}
% ---------------------------------------------------------------------------

This test investigates whether splitting ISP-provided equipment into bridge mode plus a dedicated router reduces total system power consumption compared to using the ISP device in standalone router mode.
It directly addresses \textbf{RQ8}.

\subsubsection{Devices Under Test}
\begin{description}
    \item[Configuration~A (Standalone):] Huawei EG8245W5-8T operating as router (NAT, DHCP, Wi-Fi, firewall).
        This configuration reuses the Huawei results already obtained in Test~1 (Section~\ref{sec:test-incremental-port-load}), since the protocol and load parameters are identical.
        No additional measurement run is required.
    \item[Configuration~B (Split):] Huawei EG8245W5-8T in bridge mode (minimal processing) + Asus RT-AX68U as dedicated router.
\end{description}

\subsubsection{Test Protocol}
Both configurations are tested with the same incremental port load profile as Test~1 for direct comparability:
\begin{enumerate}
    \item \textbf{Pre-test baseline} (10\,min): Cables connected, no traffic.
    \item \textbf{Load phases} (4$\times$20\,min): Incremental 1--4 port UDP flood.
    \item \textbf{Post-test baseline} (10\,min): Traffic stopped.
\end{enumerate}

\paragraph{Configuration~A:}
Reuses the Huawei standalone measurements from Test~1 (Section~\ref{sec:results-huawei}).
Because the load profile, traffic parameters, and power metering setup are identical, no additional measurement run is needed; the Huawei Test~1 data serves directly as the single-device baseline.

\paragraph{Configuration~B:}
\begin{itemize}
    \item Huawei set to bridge mode via its admin interface (disables NAT, DHCP, firewall, optionally Wi-Fi).
    \item Asus RT-AX68U configured as the primary router (WAN port connected to Huawei's LAN port).
    \item Test PC connects to the Asus's LAN ports.
    \item \textbf{Power measurement:} Both devices on a single DECT~200 via a power strip --- measures combined system power directly.
\end{itemize}

\noindent\textbf{Load generation parameters:} Identical to Test~1 (UDP, 1400\,bytes, 16 workers, 5\,s polling).

    \item[RQ8 (Fully addressed):] Comparing Configuration~A total power (Huawei standalone, from Test~1) vs.\ Configuration~B total power (Huawei bridge + Asus router) at each load level reveals whether the bridge-mode split is more or less efficient. Because Configuration~B uses a single DECT~200 measuring the combined power of both devices via a power strip, the comparison is straightforward: single-device power vs.\ two-device combined power at equivalent load phases.
\end{description}
